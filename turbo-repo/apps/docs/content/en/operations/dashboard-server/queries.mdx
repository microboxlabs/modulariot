# Connection-backed queries

A saved dashboard query names a host-owned `connectionId` and `operationId`. Viewers select that query by ID and supply named filter values. They cannot supply a URL, SQL statement, credential, or replacement operation. This lets the same server library work with different frameworks and administration tools.

```json
{
  "id": "costs",
  "variableName": "costs",
  "connectionId": "billing",
  "operationId": "cost-summary",
  "parameters": {
    "days": { "kind": "literal", "value": 30 },
    "service": { "kind": "filter", "key": "service", "defaultValue": null }
  }
}
```

## Library integration

`createDashboardQueryService` accepts the same identity, tenant, scope, store and policy adapters as access control, plus a `DashboardOperationExecutor`. Call `service.execute(request, ref, queryId, filters, signal)` from your host. For an HTTP host, pass an async callback as `filters` to defer decoding the body until after authorization. This programmatic service does not register an HTTP route automatically.

Authorization happens before loading or executing a query. A Consumer can run a query on a dashboard they can read; embed identities remain restricted to their exact dashboard. Unknown query IDs, ambiguous definitions, invalid values and undeclared filters are refused. Access decisions use the `dashboard.query` audit action; filter values and returned rows are not included in that event.

## Host responsibilities

The operation adapter must resolve an **active, read-only operation in the authorized tenant**, validate parameters against its operation schema, enforce tenant predicates, and resolve credentials on the server. Treat dashboard definitions as editor-controlled: a literal parameter is not proof of tenant authority. Keep security predicates outside editable bindings.

Bound upstream response reads before buffering. Honor the supplied abort signal and enforce datasource-specific limits, including BigQuery query-cost limits. Return `{ rows: [...] }` with JSON scalar or flat scalar-array values. Keep credentials and internal errors out of results.

## Execution limits

Defaults are 8 concurrent operations per service instance, a 20-second deadline, 5,000 rows, and 2 MiB of UTF-8 JSON. Each row has at most 100 fields. Filter values follow the contract's limits; requests allow at most 32 filters and definitions at most 100 parameters. Configure `maxConcurrent`, `timeoutMs`, `maxRows` and `maxBytes` when constructing the service.

Timeouts cancel the adapter's signal. An adapter that ignores cancellation keeps its concurrency slot until it settles, preventing repeated timeouts from creating unlimited background work. Upstream failures and invalid results become a generic `UPSTREAM_ERROR`. These instance limits complement host authentication, request-body limits and deployment rate limits; they do not replace them.

## Host execution over HTTP

A standalone pod can reuse the host's connection catalog with
`createHttpDashboardOperationExecutor({ url, proxyKey })`. Supply the executor
as `operations` when constructing the query service. The URL is a fixed,
operator-configured endpoint; dashboard values cannot change its destination.
HTTPS is required except for loopback development. Set `allowHttp: true` only
for an explicitly trusted private-network deployment.

The adapter sends a JSON `POST` authenticated by `x-miot-proxy-key` (at least
32 characters). The body contains `tenantId`, `scopeId`, `dashboardSlug`,
`userId`, `connectionId`, `operationId`, `parameters`, and
`limits: { maxRows, maxBytes }`. No user token or credential material is sent.
The host must authenticate the service key, resolve the connection within that
tenant, enforce the saved operation's read-only and parameter policies, and
answer `{ "rows": [...] }`. It must not expose this as a public unauthenticated
execution endpoint. A host may impose stricter limits than those requested.

Redirects are refused. The default HTTP deadline is 20 seconds; configure
`requestTimeoutMs` to shorten it. Caller cancellation propagates to the HTTP
request. The adapter bounds received bytes before parsing, validates row
values, discards extra response metadata, and returns a generic error on any
host failure. The host still owns upstream cancellation and cost controls.
## ModularIoT operation policy

The integrations module provides `DashboardOperationPolicy.prepare` for host
adapters. Resolve an **ACTIVE connection owned by the authorized tenant** first.
The helper validates its stored operation and binds the host's tenant code; it
does not perform that connection authorization or execute a network request.

Operations opt in through `requestSchema["x-dashboard"]`:

```json
{
  "type": "object",
  "properties": {
    "days": { "type": "integer", "minimum": 1, "maximum": 30 },
    "tenant": { "type": "string" }
  },
  "required": ["days", "tenant"],
  "additionalProperties": false,
  "x-dashboard": {
    "readOnly": true,
    "kind": "HTTP_GET",
    "tenantParameter": "tenant"
  }
}
```

`HTTP_GET` requires a stored GET operation; `BIGQUERY` requires POST and a
BigQuery-specific executor. A caller cannot supply `tenantParameter`, even with
the correct value. The host inserts it before schema validation. If credentials
already isolate the upstream account, an administrator may instead set
`credentialScoped: true` and omit `tenantParameter`. Declaring read-only access
is the connection administrator's responsibility; HTTP GET alone does not prove
an upstream operation is harmless.

Schemas must describe a closed object (`additionalProperties: false`). Draft
2020-12 is supported without remote/local references or regex rules. Schema
size, depth and node count are bounded; compiled validators use a bounded cache.
Parameters allow JSON scalars and flat scalar arrays, with the same value limits
as the dashboard contract and a 256 KiB host parameter envelope.

## ModularIoT host endpoint

The integrations module accepts `POST /internal/dashboard-operations` using the
HTTP adapter envelope above. Configure the same `miot.dashboards.proxy-key` on
both sides (at least 32 characters). Keep this service endpoint on the private
network. It trusts the authenticated dashboard service to authorize the user,
scope and dashboard; it resolves the organization slug to its tenant code and
checks the connection and operation itself.

The initial executor supports `HTTP_GET` operations returning a JSON array of
rows. It requires an ACTIVE tenant-owned connection and the opt-in policy above,
then executes the exact operation snapshot that was validated. Named parameters
are URL-encoded; scalar strings are sent literally and other values as JSON.
Stored URLs may not contain query strings or fragments, and parameters cannot
overwrite credential query parameters. Public-URL checks and credential
resolution reuse the integration invoker. BIGQUERY operations require the
separate BigQuery executor and are refused by this HTTP-only implementation.

The host permits at most eight concurrent executions, 5,000 rows and 2 MiB of
result JSON, and honors smaller requested limits. Invalid provider responses
and internal failures return a generic error without provider data. Every
endpoint response includes `Cache-Control: no-store`.
