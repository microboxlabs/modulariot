# Guardar credenciales de fuentes de datos

Un servidor independiente puede guardar él mismo las credenciales de las fuentes de datos, cifradas en su base de datos. Use esto cuando no hay ModularIoT que las guarde. Con ModularIoT, las credenciales están en la pantalla **Credenciales** de ModularIoT, y esta guía no aplica.

## Cómo se organiza

| Registro | Contiene | Quién puede leerlo |
| --- | --- | --- |
| Fuente de datos | Nombre, tipo, dirección de destino y el nombre de su credencial | Los miembros del ámbito |
| Credencial | El secreto, cifrado con AES-256-GCM | Nadie. La API solo devuelve un resumen: el tipo y los últimos caracteres. |

Ningún dashboard, respuesta de la API ni línea de log contiene el secreto.

## 1. Activar el almacén de credenciales

Genere una clave y guárdela junto con sus otros secretos:

```bash
openssl rand -base64 32
```

Inicie el servidor con esa clave y un almacén de base de datos:

```bash
MIOT_DASHBOARD_STORE=sqlite
MIOT_DASHBOARD_CREDENTIALS_KEY=<the key>
```

La clave debe tener al menos 32 caracteres, y el almacén debe ser `sqlite` o `postgres`. De lo contrario, el servidor no inicia.

<Callout type="error">
Si pierde la clave, ninguna credencial guardada se puede leer. Si la cambia, vuelva a cargar las credenciales.
</Callout>

## 2. Guardar una credencial

Esta es la única solicitud que lleva un secreto:

```bash
curl -X PUT https://dashboards.example.com/tenants/acme/scopes/ops/credentials/fleet-api \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"kind":"BEARER","token":"the-api-token"}'
```

| `kind` | Campos | Se envía al destino como |
| --- | --- | --- |
| `NONE` | ninguno | Nada |
| `BEARER` | `token` | `Authorization: Bearer …` |
| `API_KEY_HEADER` | `header`, `value` | El encabezado indicado |
| `API_KEY_QUERY` | `param`, `value` | Un parámetro de la URL |
| `BASIC` | `username`, `password` | `Authorization: Basic …` |
| `SERVICE_ACCOUNT` | `projectId`, `clientEmail`, `privateKey` | Un token de acceso de Google, para BigQuery |

Un campo mal escrito se rechaza con 400 en lugar de guardarse vacío.

## 3. Crear la fuente de datos

```bash
curl -X POST https://dashboards.example.com/tenants/acme/scopes/ops/datasources \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "name": "Fleet",
    "type": "POSTGREST",
    "isActive": true,
    "target": "https://data.acme.example/rest/v1",
    "credentialRef": "fleet-api"
  }'
```

| `type` | `target` |
| --- | --- |
| `POSTGREST` | La URL base de PostgREST. Debe ser `https` y no debe contener `user:password@`. |
| `BIGQUERY` | `project.dataset`. Con una cuenta de servicio, basta con el nombre del dataset. |

## 4. Probarla

```bash
curl -X POST https://dashboards.example.com/tenants/acme/scopes/ops/datasources/{id}/test \
  -H "Authorization: Bearer $TOKEN"
```

```json
{"data":{"testable":true,"success":true,"status":200,"testedAt":"2026-10-05T12:00:00.000Z","message":"The target answered"}}
```

| Resultado | Significa |
| --- | --- |
| `success: true` | El destino respondió con la credencial |
| `status: 401` o `403` | El destino rechazó la credencial |
| `status: 404` | El destino no existe, o la credencial no puede verlo |
| Sin `status` | No se pudo llegar al destino a tiempo |

Para probar valores antes de guardarlos, envíe el mismo cuerpo a `.../datasources/test`. Una redirección cuenta como falla, porque seguirla permitiría que el destino eligiera adónde va la credencial. La respuesta nunca incluye el cuerpo de la respuesta del destino, que podría repetir la credencial.

## Dejar que otro sistema guarde las credenciales

Si otro sistema ya administra las credenciales, defina `MIOT_DASHBOARD_CREDENTIALS_URL` en lugar de la clave. El servidor entonces pregunta a ese sistema qué encabezados enviar, y no guarda nada. Consulte [Configuración](/es/products/dashboards/reference/configuration#credenciales-de-fuentes-de-datos). Defina la URL o la clave, nunca ambas.
