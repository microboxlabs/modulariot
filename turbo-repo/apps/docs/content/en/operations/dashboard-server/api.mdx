# API

Every route names the organization and the scope, and the server checks both before answering. The full contract is at `/openapi.yaml` and can be tried at `/docs` while `MIOT_DASHBOARD_DOCS` is on.

## Routes

| Method and path | Does |
| --- | --- |
| `GET /tenants/{t}/scopes/{s}/dashboards` | Lists the dashboards the person may see |
| `GET /tenants/{t}/scopes/{s}/dashboards/{slug}` | Returns one dashboard with its revision |
| `PUT /tenants/{t}/scopes/{s}/dashboards/{slug}` | Creates or replaces a dashboard |
| `DELETE /tenants/{t}/scopes/{s}/dashboards/{slug}` | Deletes a dashboard |
| `GET …/dashboards/{slug}/capabilities` | What the person can do with that dashboard |
| `GET`, `PUT …/dashboards/{slug}/permissions` | Extra roles granted by that dashboard |
| `GET`, `POST …/datasources` | The organization's datasources |
| `GET`, `PUT`, `DELETE …/datasources/{id}` | One datasource |
| `POST …/datasources/test`, `POST …/datasources/{id}/test` | Connection test |
| `GET …/credentials`, `GET`, `PUT …/credentials/{ref}` | Credentials, always as summaries |

## Saving a dashboard

Each dashboard has an integer revision. `GET` returns it as a quoted `ETag`, such as `"3"`. Copy that header into `If-Match` when saving. A successful `PUT` returns the new `ETag` and the revision in `data.revision`. When no dashboard is stored, `GET` returns `data: null` and `ETag: "0"`; sending that value prevents overwriting a dashboard created by another editor in the meantime.

A stale revision returns `409`. Keep the unsaved edits and let the person compare them with the latest dashboard before saving again. Do not automatically retry the old document with the new revision: that would overwrite the other editor’s changes. Requests without `If-Match` remain unconditional for compatibility.

```bash
curl -X PUT http://127.0.0.1:3070/tenants/acme/scopes/operations/dashboards/fleet \
  -H "Authorization: Bearer $TOKEN" \
  -H 'If-Match: "3"' \
  -H 'Content-Type: application/json' \
  -d '{"version":2,"name":"Fleet","widgets":[],"preferences":{"editMode":false}}'
```

The document is validated against the contract before it is stored. A `version` other than `2`, or a structure that is not a dashboard, is refused with `400` naming the field. Fields the contract does not know are kept, so a document written by a newer UI passes intact through an older server.

## Errors

Every error response has the same shape:

```json
{ "error": "…", "status": 403, "code": "FORBIDDEN", "reason": "TENANT_SCOPE" }
```

| Code | When |
| --- | --- |
| `401` | No credential, or one that could not be verified |
| `403` `TENANT_SCOPE` | The person is not in the organization or scope the URL names |
| `403` `CAPABILITY` | They are, but their role does not allow the action |
| `404` | The dashboard or datasource does not exist, or the route is not mounted in this installation |
| `409` | The revision sent in `If-Match` is no longer current |
| `400` | The body does not match the contract; the message says where |
| `500` | A service the server depends on did not answer |

Messages from internal exceptions never reach the client.

## Rendering dashboards

The server API can be consumed by any frontend. Rendering and editing belong to the frontend; the server stores the document and enforces access. A separately published UI package is planned.

## ModularIoT product API

The application exposes `/api/dashboards` through its server-side session and the ModularIoT proxy. The active organization comes from authenticated membership resolution. Browser-supplied tenant identifiers and authorization headers do not select another organization or identity. The dashboard server can run in its own pod and has no Alfresco runtime dependency.

| Method | Application route | Operation |
| --- | --- | --- |
| GET | `/api/dashboards` | List dashboards |
| GET, PUT, DELETE | `/api/dashboards/{dashboard}` | Load, save, delete |
| GET | `/api/dashboards/{dashboard}/capabilities` | Read allowed actions |
| GET, PUT | `/api/dashboards/{dashboard}/permissions` | Read or replace role assignments |
| POST | `/api/dashboards/{dashboard}/queries/{query}` | Execute a saved query |

Keep the `ETag` from a load and send it as `If-Match` when saving. A `409` preserves the newer server version; retain the user's edits and resolve the conflict before retrying. The browser never needs the session's raw JWT.

These endpoints enable a parallel migration. Existing legacy dashboard pages remain available until their replacements have been validated. This API alone does not move existing documents or switch the UI.

Pass `?org={activeOrgSlug}` on requests and include the organization in client cache keys. If the active organization changed in another tab, the API returns `409` before reading or writing a dashboard. This parameter confirms the selected organization; it cannot select a different one.

## Request size

Both `createDashboardHandler` and the standalone server enforce `maxBodyBytes` (1 MiB by default). The embedded handler authorizes before reading JSON and counts received bytes, including chunked requests; an oversized body returns `413`. Configure the host’s request deadline and connection limits as well.

## Saved queries

Send `{ "filters": { ... } }` to execute a saved query. The organization-bound browser client exposes `query(slug, queryId, filters, signal)` and validates returned rows. It sends no credentials or raw SQL, and propagates cancellation through the application proxy.

## Parallel application workspace

Open **Dashboards** in the application navigation (`/app/{lang}/dashboards`). This workspace lists the active organization's server-backed dashboards. Existing `/home` dashboards remain available during migration. No legacy site lookup is needed to load these documents.

Editors save explicitly. A revision conflict retains local changes and requires an explicit reload; it never overwrites the newer document automatically. Consumers can view and query but cannot edit or delete. Stored query definitions bind widgets to operations in the existing connection catalog. The browser sends filter values, never credentials or SQL.

Enable the server's operation executor and configure the private host endpoint before validating data. Migrate each legacy widget's data binding to a saved query and compare its results before retiring its old dashboard. Specialized domain widgets still require their own compatibility validation.

Dashboard lists apply the configured per-dashboard visibility policy before returning names. Denied or concurrently deleted dashboards are omitted. Policy and storage errors fail the request instead of returning unfiltered metadata. The built-in role policy grants scope members read access; hosts that use `allowedGroups` must configure `createAllowedGroupsPolicy()`.

## Import validation

`importDashboards` defaults to a dry run. Both dry and apply runs validate the document version and shared contract before accessing the store. Malformed preferences, widgets, or saved queries are reported in `refused` with field paths; no document is written. Extension fields are preserved. A valid document still needs live datasource, filter and permission acceptance before replacing its legacy dashboard.

`migratePlannerQueries(config, mappings)` prepares planner requests for import using an explicit connection, operation and parameter map for every request. It preserves IDs, variable names, widgets and filters, removes legacy request definitions, and refuses partial or ambiguous mappings and existing saved queries. It performs no writes or network calls. Review parameter defaults, tenant isolation and any direct-datasource widgets separately; conversion does not establish live compatibility.
