# Hoja de ruta del servidor de dashboards

El objetivo de entrega es una biblioteca npm segura y portable que también funcione como pod independiente. Alfresco y Java no son runtimes obligatorios. ModularIoT es una integración de host; embeber el servidor en Next.js u otra tecnología de administración no debe exigir adoptar su backend.

## Obligatorio: ejecución portable de consultas en TypeScript

Es un requisito de aceptación de la entrega, no una mejora opcional. Los proveedores TypeScript portables de BigQuery y HTTP están implementados. ModularIoT resuelve planes autorizados de conexión/plantilla/credencial mediante su endpoint privado de catálogo; el servidor de dashboards ejecuta las consultas. Otros hosts aportan su propio adaptador sin requerir Java ni Alfresco. El pod independiente está desplegado en dev y el dashboard de facturación pasó la validación en navegador. Siguen pendientes la migración de telemetría y la aceptación de Consumer en navegador.

- [x] Implementar ejecución de BigQuery en TypeScript dentro del paquete: parámetros tipados, dry run que acepte solo SELECT, límites de lectura y facturación, plazos, cancelación y límites de filas y bytes.
- [x] Implementar operaciones HTTP/PostgREST portables de solo lectura, con validación de destinos, parámetros de tenant impuestos por el servidor, esquemas cerrados y respuestas limitadas.
- [x] Separar ejecución y resolución del catálogo. Un adaptador confiable resuelve la conexión/plantilla activa y autorizada y su credencial bajo el tenant verificado; los dashboards contienen referencias y filtros declarados, nunca credenciales ni SQL/URLs arbitrarios.
- [x] Integrar las conexiones/plantillas/credenciales existentes de ModularIoT mediante ese adaptador, sin duplicar el catálogo de datasources. Mantener la ejecución remota en Java como opción durante la migración.
- [x] Conectar el ejecutor portable a la configuración standalone y documentar sus exports npm para hosts embebidos.
- [x] Ejecutar el paquete npm compilado localmente contra la base real de facturación **sin ningún proceso Quarkus ni endpoint de ejecución Java**, tanto embebido como standalone. Las pruebas unitarias no cierran este punto.

## Evidencia y límites actuales

La validación local del paquete compilado obtuvo 13 filas reales de facturación tanto mediante el listener Node embebido como mediante el CLI independiente, usando el proveedor TypeScript sin servicio de ejecución Java. Ambos recorridos verificaron JWT y rechazaron solicitudes sin autenticación con 401. Otra prueba local usó el catálogo real de ModularIoT y su servicio de credenciales cifradas: el CLI compilado obtuvo 13 filas reales de facturación con una solicitud al catálogo, tres a Google y ninguna solicitud de ejecución Java. La suite del producto pasó 2.002 pruebas, con una omitida, tras los cambios del espacio paralelo. La suite combinada del servidor 0.4.0 pasó 1.180 pruebas con una omitida, incluidas pruebas reales de inicio y recuperación en PostgreSQL local. La aceptación de la migración en navegador sigue pendiente. Los widgets legados especializados requieren validación individual.

Una instalación nueva desde el registro de ambos paquetes 0.4.0 verificó los 11 exports del servidor, la carga del módulo de operaciones incluido, el inicio del CLI con SQLite, el rechazo sin autenticación, las restricciones de grupos en listas/lecturas/consultas y el rechazo de escrituras de Consumer. El CLI instalado también verificó la omisión de filtros HTTP opcionales y la conservación del tenant contra un servicio RPC local. El ejecutor BigQuery publicado obtuvo 13 filas reales de facturación tanto directamente como mediante un listener Node embebido autenticado, con un límite de facturación de 1 GB y sin servicio de ejecución Java. Estas pruebas desde el registro verifican el comportamiento del paquete; la aceptación en navegador se registra por separado a continuación.

## Aceptación en dev — 2026-09-29

El despliegue en dev utiliza la imagen `sha-43ae9ae` del servidor de dashboards y la imagen `sha-aab43fa` de la aplicación. El pod independiente resuelve planes autorizados del catálogo mediante ModularIoT y ejecuta BigQuery en Node. La validación del despliegue incluyó comprobaciones de manifiestos y renderizado de Helm, disponibilidad, rechazo sin autenticación y respaldo y comprobación de integridad de SQLite.

El piloto de facturación autenticado mostró 13 filas reales de servicios de la base de facturación. Seleccionar un servicio redujo la tabla a la fila correspondiente; restaurar todos los servicios recuperó los resultados. Un Owner de la organización creó un dashboard desde la interfaz y abrió su editor; después se eliminó el dashboard temporal. Los dashboards respaldados por el servidor ya no muestran un control de fecha implícito cuando su configuración guardada no declara ninguno.

Una operación aislada con un límite de facturación de un byte se rechazó después de que su dry run estimara 146.865.127 bytes, antes de enviar un trabajo de consulta facturable. El navegador mostró un error genérico de consulta. Se eliminó el dashboard temporal de error; su operación de validación con límite de un byte permanece en el catálogo. Los intentos de enviar filtros no declarados de SQL o proyecto, o sustituir la conexión en el cuerpo de la solicitud, recibieron 400. Tres solicitudes simultáneas de facturación devolvieron 13 filas cada una; es una comprobación básica, no una medición de capacidad.

Estas comprobaciones usaron una cuenta Owner y no demuestran acceso de Consumer ni aislamiento entre tenants. El piloto de telemetría aún necesita verificar la correspondencia entre el alcance de datos legado y la organización de dev antes de migrar sus operaciones. Los dashboards existentes siguen disponibles hasta completar esas comprobaciones de aceptación y las comparaciones de compatibilidad de widgets.
