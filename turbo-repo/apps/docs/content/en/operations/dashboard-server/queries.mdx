# Connection-backed queries

A saved dashboard query names a host-owned `connectionId` and `operationId`. Viewers select that query by ID and supply named filter values. They cannot supply a URL, SQL statement, credential, or replacement operation. This lets the same server library work with different frameworks and administration tools.

```json
{
  "id": "costs",
  "variableName": "costs",
  "connectionId": "billing",
  "operationId": "cost-summary",
  "parameters": {
    "days": { "kind": "literal", "value": 30 },
    "service": { "kind": "filter", "key": "service", "defaultValue": null }
  }
}
```

## Library integration

`createDashboardQueryService` accepts the same identity, tenant, scope, store and policy adapters as access control, plus a `DashboardOperationExecutor`. Call `service.execute(request, ref, queryId, filters, signal)` from your host. For an HTTP host, pass an async callback as `filters` to defer decoding the body until after authorization. Set `queries: { operations: executor }` on `createDashboardHandler` or `serve` to enable `POST /tenants/{tenantId}/scopes/{scopeId}/dashboards/{slug}/queries/{queryId}`. Its JSON body is `{ "filters": {} }` and its response is `{ "data": { "rows": [] } }`. The route returns 404 when no executor is configured. It authorizes before decoding the body and uses the configured request byte limit.

Authorization happens before loading or executing a query. A Consumer can run a query on a dashboard they can read; embed identities remain restricted to their exact dashboard. Unknown query IDs, ambiguous definitions, invalid values and undeclared filters are refused. Access decisions use the `dashboard.query` audit action; filter values and returned rows are not included in that event.

## Host responsibilities

The operation adapter must resolve an **active, read-only operation in the authorized tenant**, validate parameters against its operation schema, enforce tenant predicates, and resolve credentials on the server. Treat dashboard definitions as editor-controlled: a literal parameter is not proof of tenant authority. Keep security predicates outside editable bindings.

Bound upstream response reads before buffering. Honor the supplied abort signal and enforce datasource-specific limits, including BigQuery query-cost limits. Return `{ rows: [...] }` with JSON scalar or flat scalar-array values. Keep credentials and internal errors out of results.

## Execution limits

Defaults are 8 concurrent operations per service instance, a 20-second deadline, 5,000 rows, and 2 MiB of UTF-8 JSON. Each row has at most 100 fields. Filter values follow the contract's limits; requests allow at most 32 filters and definitions at most 100 parameters. Configure `maxConcurrent`, `timeoutMs`, `maxRows` and `maxBytes` when constructing the service.

Timeouts cancel the adapter's signal. The standalone HTTP server also cancels it when the client disconnects before the response completes. An adapter that ignores cancellation keeps its concurrency slot until it settles, preventing repeated timeouts from creating unlimited background work. Upstream failures and invalid results become a generic `UPSTREAM_ERROR`. These instance limits complement host authentication, request-body limits and deployment rate limits; they do not replace them.

## ModularIoT operation policy

The integrations module provides `DashboardOperationPolicy.prepare` for host
adapters. Resolve an **ACTIVE connection owned by the authorized tenant** first.
The helper validates its stored operation and binds the host's tenant code; it
does not perform that connection authorization or execute a network request.

Operations opt in through `requestSchema["x-dashboard"]`:

```json
{
  "type": "object",
  "properties": {
    "days": { "type": "integer", "minimum": 1, "maximum": 30 },
    "tenant": { "type": "string" }
  },
  "required": ["days", "tenant"],
  "additionalProperties": false,
  "x-dashboard": {
    "readOnly": true,
    "kind": "HTTP_GET",
    "tenantParameter": "tenant"
  }
}
```

`HTTP_GET` requires a stored GET operation; `BIGQUERY` requires POST and a
BigQuery-specific executor. A caller cannot supply `tenantParameter`, even with
the correct value. The host inserts it before schema validation. If credentials
already isolate the upstream account, an administrator may instead set
`credentialScoped: true` and omit `tenantParameter`. Declaring read-only access
is the connection administrator's responsibility; HTTP GET alone does not prove
an upstream operation is harmless.

Schemas must describe a closed object (`additionalProperties: false`). Draft
2020-12 is supported without remote/local references or regex rules. Schema
size, depth and node count are bounded; compiled validators use a bounded cache.
Parameters allow JSON scalars and flat scalar arrays, with the same value limits
as the dashboard contract and a 256 KiB host parameter envelope.

## Host execution over HTTP

A standalone pod can reuse the host's connection catalog with
`createHttpDashboardOperationExecutor({ url, proxyKey })`. Supply the executor
as `operations` when constructing the query service. The URL is a fixed,
operator-configured endpoint; dashboard values cannot change its destination.
HTTPS is required except for loopback development. Set `allowHttp: true` only
for an explicitly trusted private-network deployment.

The adapter sends a JSON `POST` authenticated by `x-miot-proxy-key` (at least
32 characters). The body contains `tenantId`, `scopeId`, `dashboardSlug`,
`userId`, `connectionId`, `operationId`, `parameters`, and
`limits: { maxRows, maxBytes }`. No user token or credential material is sent.
The host must authenticate the service key, resolve the connection within that
tenant, enforce the saved operation's read-only and parameter policies, and
answer `{ "rows": [...] }`. It must not expose this as a public unauthenticated
execution endpoint. A host may impose stricter limits than those requested.

Redirects are refused. The default HTTP deadline is 20 seconds; configure
`requestTimeoutMs` to shorten it. Caller cancellation propagates to the HTTP
request. The adapter bounds received bytes before parsing, validates row
values, discards extra response metadata, and returns a generic error on any
host failure. The host still owns upstream cancellation and cost controls.

## ModularIoT host endpoint

The integrations module accepts `POST /internal/dashboard-operations` using the
HTTP adapter envelope above. Configure the same `miot.dashboards.proxy-key` on
both sides (at least 32 characters). Keep this service endpoint on the private
network. It trusts the authenticated dashboard service to authorize the user,
scope and dashboard; it resolves the organization slug to its tenant code and
checks the connection and operation itself.

The HTTP executor supports `HTTP_GET` operations returning a JSON array of
rows. It requires an ACTIVE tenant-owned connection and the opt-in policy above,
then executes the exact operation snapshot that was validated. Named parameters
are URL-encoded; scalar strings are sent literally and other values as JSON.
Stored URLs may not contain query strings or fragments, and parameters cannot
overwrite credential query parameters. Public-URL checks and credential
resolution reuse the integration invoker. BIGQUERY operations use the bounded
executor described below.

The host permits at most eight concurrent executions, 5,000 rows and 2 MiB of
result JSON, and honors smaller requested limits. Invalid provider responses
and internal failures return a generic error without provider data. Every
endpoint response includes `Cache-Control: no-store`.

The ingress authenticates before body buffering or JSON decoding and limits requests to 512 KiB, including chunked bodies. Framework-generated errors also carry the no-store header.

## BigQuery saved operations

Use the existing BigQuery connection and its Google service-account credential.
Its base URL must be `https://bigquery.googleapis.com`; configure the credential's
OAuth scope as `https://www.googleapis.com/auth/bigquery` for the jobs API. The
service account still needs only the required job execution and dataset read
permissions; the OAuth scope does not grant additional IAM permissions.

A POST operation opts in with `kind: "BIGQUERY"` and the normal isolation policy.
Its `x-dashboard` settings also contain `projectId`, `location`, the saved `query`,
`maximumBytesBilled` (a decimal string), and `parameterTypes` (a map from each
bound parameter name to its BigQuery type). Types include `STRING`, `INT64`,
`FLOAT64`, `NUMERIC`, `BIGNUMERIC`, `BOOL`, `DATE`, `DATETIME`, `TIME`, `TIMESTAMP`
and flat arrays such as `ARRAY<STRING>`. Use an empty map when there are no
parameters. SQL uses named placeholders such as `@days`; values are never
interpolated into SQL. Editors and viewers cannot send SQL or job settings.

Every execution performs a dry run and requires statement type SELECT and an
estimated scan within the saved billing limit. The operation limit cannot exceed
`miot.dashboards.bigquery.maximum-bytes-billed` (default 1,000,000,000 bytes).
Submitted jobs carry the same billing cap and a 20-second job timeout; the host
also enforces a total request deadline and attempts cancellation on failure.
Only complete, bounded scalar-column results are returned. Nested/repeated
columns and paginated results are refused; shape the saved SQL for dashboard
consumption. No query results are logged by this executor.



## Portable TypeScript BigQuery executor

The npm `@microboxlabs/miot-dashboard-server/queries` export provides `createBigQueryOperationExecutor`. Supply a trusted `resolve(request)` callback that checks the active tenant-owned connection/template, applies tenant predicates, and returns `{ plan, parameters, accessToken }` or `null`. The plan contains `projectId`, `location`, operator-owned `sql`, `maximumBytesBilled`, and a closed `parameterTypes` map. Honor the request signal during catalog and credential resolution.

Execution calls Google directly without Quarkus or Alfresco. SELECT dry-run validation, host/template billing limits, deadlines, cancellation and bounded complete flat results are enforced in TypeScript. The default host billing cap is 1 GB. Use `MIOT_DASHBOARD_OPERATIONS_MODULE` to load an operator-installed factory in the standalone CLI (see [configuration](./configuration)). The ModularIoT catalog resolver remains an open roadmap item; the existing HTTP execution path remains available during migration.

## Portable HTTP/PostgREST provider

`createHttpGetOperationExecutor` from `@microboxlabs/miot-dashboard-server/queries` executes saved GET operations directly, without Java. Its trusted `resolve(request)` callback resolves an active, authorized connection/template and credential under the verified tenant. Configure exact operator-owned `allowedOrigins`; dashboard editors cannot supply destinations.

The resolved plan contains `readOnly: true`, `url` (no query or fragment), closed scalar `parameterTypes` (`string`, `number`, `boolean`), matching `parameters`, and `isolation`. Use `{ tenantParameter, tenantValue }` to inject a server-resolved tenant predicate; input parameters cannot contain that name. Use `{ credentialScoped: true }` only when the host verifies that the upstream credential itself isolates the tenant. Optional credential `headers` accept only `authorization`, `x-api-key` and `apikey`.

The provider performs GET only and requests `Prefer: count=exact`. It rejects redirects, HTTP 206, incomplete or unknown `Content-Range`, nested row objects and oversized responses. Limits are at most 20 seconds, eight concurrent calls, 5,000 rows and 2 MiB. Hosts must honor the resolver's cancellation signal and choose read-only credentials/functions. Exact allowed origins are trusted services, not a DNS firewall: apply deployment egress policy as well. Private HTTP requires explicit `allowHttp: true`; loopback is available for local validation.

Use it through the same `queries: { operations: executor }` seam or standalone operation module as the BigQuery provider. The ModularIoT catalog adapter and real telemetry migration remain separate acceptance gates.
