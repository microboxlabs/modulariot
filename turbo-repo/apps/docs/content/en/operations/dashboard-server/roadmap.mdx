# Dashboard server roadmap

The completion target is a secure, portable npm library that also runs as a standalone pod. Alfresco and Java are not required runtimes. ModularIoT is one host integration; embedding in Next.js or a different administration framework must not require adopting ModularIoT's backend.

## Mandatory: portable TypeScript query execution

This is a release acceptance requirement, not an optional follow-up. Portable TypeScript BigQuery and HTTP providers are implemented. ModularIoT resolves authorized connection/template/credential plans through its private catalog endpoint; the dashboard server executes the queries. Other hosts supply their own resolver without requiring Java or Alfresco. Dev rollout and browser acceptance remain open.

- [x] Implement TypeScript BigQuery execution in the dashboard server package, including typed parameters, SELECT-only dry runs, scan and billing limits, deadlines, cancellation, and bounded result rows and bytes.
- [x] Implement portable read-only HTTP/PostgREST operation execution with destination validation, tenant parameter enforcement, closed parameter schemas, and response limits.
- [x] Separate query execution from catalog resolution. A trusted host adapter resolves an authorized, active connection/template and server-side credential under the verified tenant; dashboard documents hold references and declared filter bindings, never credentials or arbitrary SQL/URLs.
- [x] Integrate ModularIoT's existing connections/templates/credentials through that resolver. Do not introduce another ModularIoT datasource catalog. Keep remote Java execution optional during migration.
- [x] Wire the portable executor into standalone configuration and expose documented npm exports for embedded hosts.
- [x] Run the built npm package locally against the real billing database **with no Quarkus process or execution endpoint**, and validate it through an embedded host as well as the standalone server. Unit tests alone do not close this item.

## Parallel migration and product acceptance

- [x] Forward product requests through authenticated server routes and preserve ETag/If-Match concurrency.
- [x] Add organization-scoped dashboard pages, navigation, controlled editor storage, and saved-query widget bindings.
- [ ] Validate a signed-in Consumer with no legacy site role in the browser, including rejected writes.
- [ ] Migrate one existing Coordinador telemetry dashboard using connection/template operations; compare its rendered data and filters with the existing dashboard.
- [ ] Build and validate a dashboard for the BigQuery billing database, including query cost limits and failure states.
- [ ] Deploy the separate pod through `miot-deployments`, validate the complete product path, and publish compatible npm packages.
- [ ] Remove the old implementation only after replacement acceptance. Keep existing dashboards available throughout validation.

## Evidence and current limits

Local validation of the built package returned 13 live billing rows through both the embedded Node listener and standalone CLI using the TypeScript provider, with no Java execution service. Both paths verified JWTs and rejected unauthenticated requests with 401. A separate local integration test used the real ModularIoT catalog and encrypted credential service: the built CLI returned 13 live billing rows with one catalog request, three Google requests, and zero Java execution requests. The product application suite passed 2,002 tests with one skipped after the parallel workspace changes. The combined server suite passed 1,163 tests with one skipped, including real local PostgreSQL startup/recovery tests. Browser migration acceptance is still open. Specialized legacy widgets require individual compatibility validation.
