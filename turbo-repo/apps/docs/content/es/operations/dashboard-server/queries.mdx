# Consultas basadas en conexiones

Una consulta guardada identifica una conexión y operación del host mediante `connectionId` y `operationId`. Los lectores seleccionan la consulta por ID y envían valores de filtros. No pueden enviar una URL, SQL, credenciales ni otra operación. El mismo servidor puede integrarse con distintos frameworks y herramientas de administración.

```json
{
  "id": "costs",
  "variableName": "costs",
  "connectionId": "billing",
  "operationId": "cost-summary",
  "parameters": {
    "days": { "kind": "literal", "value": 30 },
    "service": { "kind": "filter", "key": "service", "defaultValue": null }
  }
}
```

## Integración de la biblioteca

`createDashboardQueryService` recibe los adaptadores de identidad, tenant, ámbito, almacenamiento y políticas del control de acceso, además de un `DashboardOperationExecutor`. El host llama a `service.execute(request, ref, queryId, filters, signal)`. En un host HTTP, pasa una función asíncrona como `filters` para leer el cuerpo después de autorizar. Configura `queries: { operations: executor }` en `createDashboardHandler` o `serve` para habilitar `POST /tenants/{tenantId}/scopes/{scopeId}/dashboards/{slug}/queries/{queryId}`. El cuerpo JSON es `{ "filters": {} }` y la respuesta es `{ "data": { "rows": [] } }`. Sin ejecutor, la ruta responde 404. Autoriza antes de leer el cuerpo y aplica el límite de bytes configurado.

La autorización ocurre antes de cargar o ejecutar una consulta. Un Consumer puede consultar un dashboard al que tiene acceso; las identidades embed siguen limitadas a su dashboard exacto. Se rechazan IDs desconocidos, definiciones ambiguas, valores inválidos y filtros no declarados. Las decisiones de acceso usan el evento `dashboard.query`, sin incluir valores de filtros ni filas.

## Responsabilidades del host

El adaptador debe resolver una **operación activa y de solo lectura dentro del tenant autorizado**, validar sus parámetros, aplicar las restricciones del tenant y resolver las credenciales en el servidor. Las definiciones son editables: un parámetro literal no acredita autoridad sobre un tenant. Mantén las restricciones de seguridad fuera de los parámetros editables.

Limita las lecturas de respuestas antes de cargarlas en memoria. Respeta la señal de cancelación y aplica límites propios del origen, incluidos los costos de BigQuery. Devuelve `{ rows: [...] }` con valores escalares JSON o arreglos planos de escalares. No incluyas credenciales ni errores internos en los resultados.

## Límites de ejecución

Por defecto: 8 operaciones simultáneas por instancia, 20 segundos, 5.000 filas y 2 MiB de JSON UTF-8. Cada fila admite hasta 100 campos. Los valores siguen los límites del contrato; se admiten hasta 32 filtros y 100 parámetros por definición. Configura `maxConcurrent`, `timeoutMs`, `maxRows` y `maxBytes` al crear el servicio.

Un timeout cancela la señal del adaptador. El servidor HTTP independiente también la cancela cuando el cliente se desconecta antes de completar la respuesta. Si el adaptador ignora la cancelación, mantiene su cupo hasta terminar, evitando trabajo ilimitado en segundo plano. Los fallos y resultados inválidos se convierten en `UPSTREAM_ERROR`. Estos límites complementan la autenticación, el tamaño máximo del cuerpo HTTP y los límites de solicitudes del despliegue.

## Política de operaciones de ModularIoT

El módulo de integraciones ofrece `DashboardOperationPolicy.prepare` para los
adaptadores del host. Primero resuelve una **conexión ACTIVE del tenant
autorizado**. El helper valida la operación guardada e incorpora el código del
tenant del host; no autoriza la conexión ni ejecuta solicitudes de red.

Las operaciones se habilitan mediante `requestSchema["x-dashboard"]`:

```json
{
  "type": "object",
  "properties": {
    "days": { "type": "integer", "minimum": 1, "maximum": 30 },
    "tenant": { "type": "string" }
  },
  "required": ["days", "tenant"],
  "additionalProperties": false,
  "x-dashboard": {
    "readOnly": true,
    "kind": "HTTP_GET",
    "tenantParameter": "tenant"
  }
}
```

`HTTP_GET` exige una operación GET; `BIGQUERY` exige POST y un ejecutor específico
de BigQuery. El cliente no puede enviar `tenantParameter`, aunque su valor sea
correcto. El host lo agrega antes de validar el esquema. Si las credenciales ya
aíslan la cuenta de origen, un administrador puede declarar
`credentialScoped: true` y omitir `tenantParameter`. El administrador debe
verificar que la operación sea de solo lectura; usar GET no lo garantiza.

El esquema debe describir un objeto cerrado (`additionalProperties: false`).
Se admite Draft 2020-12 sin referencias locales/remotas ni reglas regex. Se
limitan tamaño, profundidad y cantidad de nodos; los validadores compilados usan
una caché acotada. Los parámetros admiten escalares JSON y arreglos planos con
los mismos límites de valores del contrato y un máximo de 256 KiB en el host.

## Ejecución HTTP en el host

Un pod independiente puede reutilizar el catálogo de conexiones del host con
`createHttpDashboardOperationExecutor({ url, proxyKey })`. Entrega ese ejecutor
como `operations` al crear el servicio de consultas. La URL es un endpoint fijo
configurado por el operador; los valores del dashboard no pueden cambiar el
destino. Se exige HTTPS salvo para desarrollo en loopback. Usa `allowHttp: true`
solo en un despliegue explícitamente confiable dentro de una red privada.

El adaptador envía un `POST` JSON autenticado mediante `x-miot-proxy-key` (al
menos 32 caracteres). El cuerpo contiene `tenantId`, `scopeId`, `dashboardSlug`,
`userId`, `connectionId`, `operationId`, `parameters` y
`limits: { maxRows, maxBytes }`. No envía tokens de usuario ni credenciales del
origen. El host debe autenticar la clave de servicio, resolver la conexión dentro
del tenant, aplicar las políticas de solo lectura y parámetros de la operación
guardada, y responder `{ "rows": [...] }`. No debe publicar este endpoint sin
autenticación. Puede aplicar límites más estrictos que los solicitados.

Se rechazan las redirecciones. El plazo HTTP predeterminado es de 20 segundos;
usa `requestTimeoutMs` para reducirlo. La cancelación del cliente se propaga a
la solicitud HTTP. El adaptador limita los bytes recibidos antes de parsearlos,
valida los valores de las filas, descarta metadatos adicionales y devuelve un
error genérico ante fallos del host. El host sigue siendo responsable de la
cancelación y del control de costos del origen.

## Endpoint de ejecución de ModularIoT

El módulo de integraciones acepta `POST /internal/dashboard-operations` con el
cuerpo del adaptador HTTP descrito arriba. Configure la misma clave
`miot.dashboards.proxy-key` en ambos servicios (al menos 32 caracteres) y mantenga
este endpoint en la red privada. Confía en que el servidor autenticado de
dashboards autorice al usuario, ámbito y dashboard; convierte el slug de la
organización a su código de tenant y verifica la conexión y operación.

El ejecutor HTTP admite operaciones `HTTP_GET` que devuelven un arreglo JSON
de filas. Exige una conexión ACTIVE del tenant y la política explícita anterior,
y ejecuta exactamente la operación que validó. Codifica los parámetros en la URL;
las cadenas se envían literalmente y los demás valores como JSON. Las URL guardadas
no pueden incluir query strings ni fragmentos, y los parámetros no pueden reemplazar
los de las credenciales. Reutiliza la validación de URL públicas y las credenciales
del invocador de integraciones. Las operaciones BIGQUERY usan el ejecutor
acotado descrito a continuación.

El host permite hasta ocho ejecuciones simultáneas, 5.000 filas y 2 MiB de JSON,
y respeta límites solicitados menores. Los errores internos y respuestas inválidas
del proveedor producen un error genérico sin datos privados. Todas las respuestas
incluyen `Cache-Control: no-store`.

El ingreso autentica antes de almacenar el cuerpo o decodificar JSON y limita las solicitudes a 512 KiB, incluidos los cuerpos fragmentados. Los errores generados por el framework también incluyen la cabecera no-store.

## Operaciones guardadas de BigQuery

Reutilice la conexión BigQuery y su credencial de cuenta de servicio de Google.
Su URL base debe ser `https://bigquery.googleapis.com`; configure el scope OAuth
`https://www.googleapis.com/auth/bigquery` para la API de trabajos. La cuenta de
servicio solo necesita los permisos de ejecución de trabajos y lectura del dataset;
el scope OAuth no concede permisos IAM adicionales.

Una operación POST habilita `kind: "BIGQUERY"` junto con la política de aislamiento.
Sus opciones `x-dashboard` también incluyen `projectId`, `location`, el SQL
`query` guardado, `maximumBytesBilled` (cadena decimal) y `parameterTypes`, un mapa
del nombre de cada parámetro vinculado a su tipo BigQuery. Se admiten `STRING`,
`INT64`, `FLOAT64`, `NUMERIC`, `BIGNUMERIC`, `BOOL`, `DATE`, `DATETIME`, `TIME`,
`TIMESTAMP` y arreglos planos como `ARRAY<STRING>`. Use un mapa vacío si no hay
parámetros. El SQL usa parámetros nombrados como `@days`; los valores nunca se
interpolan en el SQL. Editores y lectores no pueden enviar SQL ni opciones del trabajo.

Cada ejecución hace primero un dry run y exige una sentencia SELECT cuya lectura
estimada no supere el límite guardado. Ese límite no puede superar
`miot.dashboards.bigquery.maximum-bytes-billed` (1.000.000.000 bytes por defecto).
Los trabajos llevan el mismo límite de facturación y un plazo de 20 segundos;
el host aplica además un plazo total e intenta cancelar ante un error.
Solo devuelve resultados completos y acotados con columnas escalares. Rechaza
columnas anidadas o repetidas y resultados paginados; adapte el SQL guardado al
dashboard. Este ejecutor no registra las filas en logs.



## Ejecutor portable de BigQuery en TypeScript

El export npm `@microboxlabs/miot-dashboard-server/queries` ofrece `createBigQueryOperationExecutor`. Proporciona un callback confiable `resolve(request)` que valide la conexión/plantilla activa del tenant, imponga sus predicados y devuelva `{ plan, parameters, accessToken }` o `null`. El plan contiene `projectId`, `location`, `sql` definido por el operador, `maximumBytesBilled` y un mapa cerrado `parameterTypes`. Respeta la señal de cancelación al resolver catálogo y credenciales.

La ejecución llama directamente a Google sin Quarkus ni Alfresco. TypeScript aplica dry run de SELECT, límites de facturación del host y la plantilla, plazos, cancelación y resultados planos completos y acotados. El límite de facturación predeterminado es 1 GB. Utilice `MIOT_DASHBOARD_OPERATIONS_MODULE` para cargar una fábrica instalada por el operador en el CLI independiente (ver [configuración](./configuracion)). El resolver optativo de ModularIoT se describe abajo; la conexión del cliente portable y el recorrido de facturación en dev están validados (ver la [hoja de ruta](./roadmap)). La ejecución HTTP existente continúa disponible durante la migración.

## Resolución de planes en ModularIoT

Para ejecución portable, el host expone `POST /internal/dashboard-operations/resolve` protegido por la clave de servicio existente. Recibe la misma identidad autorizada, referencia de dashboard, identificadores de conexión/operación, parámetros y límites que el puente de ejecución, pero devuelve `{ kind, operation }` para `BIGQUERY` o `HTTP_GET` sin ejecutar la consulta de datos. Habilítelo expresamente con `miot.dashboards.plan-resolution.enabled=true`; está deshabilitado por defecto.

Reutiliza la conexión activa del tenant, el esquema cerrado de la operación y la política `x-dashboard` de solo lectura y aislamiento. BigQuery devuelve un plan validado y un token OAuth resuelto, nunca la clave privada de la cuenta de servicio. HTTP devuelve URL, valores de entrada y cabeceras de credencial permitidas; rechaza credenciales en query strings y destinos sin HTTPS. El proveedor TypeScript debe aplicar además su propia lista de orígenes permitidos y límites.

Es una respuesta sensible entre servicios, siempre con `Cache-Control: no-store`. Mantenga el endpoint en la red privada, proteja la clave compartida y nunca reenvíe la respuesta al navegador ni a logs. El servicio de dashboards debe autorizar usuario y dashboard antes de solicitar un plan. ModularIoT resuelve su catálogo; la biblioteca npm sigue independiente y otros hosts aportan su propio adaptador. El cliente portable y el despliegue deben configurarse antes de sustituir la ejecución remota.

## Proveedor HTTP/PostgREST portable

`createHttpGetOperationExecutor`, desde `@microboxlabs/miot-dashboard-server/queries`, ejecuta operaciones GET guardadas directamente, sin Java. Su callback confiable `resolve(request)` resuelve una conexión/plantilla activa y autorizada y su credencial bajo el tenant verificado. Configure `allowedOrigins` exactos del operador; los editores no proporcionan destinos.

El plan resuelto contiene `readOnly: true`, `url` sin query ni fragmento, `parameterTypes` escalares cerrados (`string`, `number`, `boolean`), `parameters` correspondientes e `isolation`. Use `{ tenantParameter, tenantValue }` para inyectar el predicado de tenant resuelto por el servidor; los parámetros de entrada no pueden contener ese nombre. Use `{ credentialScoped: true }` solo si el host verifica que la propia credencial aísla el tenant. Los `headers` opcionales admiten únicamente `authorization`, `x-api-key` y `apikey`.

El proveedor solo ejecuta GET y solicita `Prefer: count=exact`. Rechaza redirecciones, HTTP 206, `Content-Range` incompleto o desconocido, objetos anidados en filas y respuestas excesivas. Los máximos son 20 segundos, ocho llamadas simultáneas, 5.000 filas y 2 MiB. El host debe respetar la cancelación al resolver y elegir credenciales/funciones de solo lectura. Los orígenes permitidos son servicios confiables, no un firewall DNS: aplique también políticas de egreso. HTTP privado requiere `allowHttp: true`; loopback está disponible para validación local.

Se utiliza mediante `queries: { operations: executor }` o el módulo standalone, como el proveedor BigQuery. El resolver optativo de ModularIoT se describe arriba; la conexión del cliente portable está implementada; la migración de telemetría histórica queda excluida de la aceptación actual por decisión del responsable del proyecto (ver la [hoja de ruta](./roadmap)).

## Conectar proveedores portables al catálogo del host

El export npm `createRemotePlanOperationExecutor` consulta un endpoint privado de resolución de planes y después ejecuta BigQuery o HTTP GET en el proceso Node del dashboard. No delega la ejecución de consultas al endpoint. Resolución y ejecución comparten un máximo de 20 segundos y ocho llamadas simultáneas; solicitudes y respuestas de planes se limitan a 512 KiB. Solo se devuelven filas de datos finales.

En la imagen oficial, monte el módulo del operador en modo solo lectura dentro de `/app` (por ejemplo `/app/operations.mjs`) y seleccione esa ruta con `MIOT_DASHBOARD_OPERATIONS_MODULE`. La imagen conserva los exports del paquete para usar el import npm desde módulos dentro de `/app`:

```js
import { createRemotePlanOperationExecutor } from '@microboxlabs/miot-dashboard-server/queries';

export function createDashboardOperations() {
  return createRemotePlanOperationExecutor({
    url: process.env.DASHBOARD_PLAN_URL,
    proxyKey: process.env.DASHBOARD_PLAN_KEY,
    allowedDataOrigins: ['https://pgrest.streamhub.cl'],
    maximumBytesBilled: 1_000_000_000,
  });
}
```

En ModularIoT, la URL termina en `/internal/dashboard-operations/resolve`; habilite explícitamente la resolución en el host. Inyecte la clave mediante un secreto del despliegue. HTTP privado para el catálogo requiere `allowHttp: true`; el transporte HTTP de datos tiene su propio permiso `allowDataHttp`. Destinos y credenciales permanecen separados. Una lista de orígenes vacía permite despliegues solo BigQuery. Los hosts embebidos pasan el ejecutor como `queries.operations` o aportan su propio adaptador local a cada proveedor.


La imagen oficial incluye `/app/examples/modulariot-operations.mjs`, de modo que la integración estándar no necesita montar código personalizado. Selecciónelo con `MIOT_DASHBOARD_OPERATIONS_MODULE`, configure `MIOT_DASHBOARD_PLAN_URL` y reutilice `MIOT_DASHBOARD_PROXY_KEY` desde el secreto existente. `MIOT_DASHBOARD_DATA_ORIGINS` contiene orígenes permitidos separados por comas. Use `MIOT_DASHBOARD_PLAN_ALLOW_HTTP=true` solo para el catálogo privado del clúster; HTTP de datos tiene su propia opción `MIOT_DASHBOARD_DATA_ALLOW_HTTP`. Ambas opciones solo aceptan `true` o `false`. El módulo mantiene el límite de facturación predeterminado de 1 GB; otros hosts pueden aportar una fábrica propia.

## Filtros opcionales durante la migración

Un vínculo de filtro puede usar `omitWhenEmpty: true` para omitir valores ausentes o cadenas vacías. Los valores ausentes usan primero `defaultValue`, si existe; una cadena vacía explícita no usa ese valor por defecto. Se conservan null, false, cero, arreglos vacíos, espacios y cadenas de operadores. Los vínculos sin esta opción mantienen su comportamiento. El esquema de la operación debe permitir omitir el parámetro y seguir imponiendo el aislamiento del tenant. Esto permite conservar argumentos opcionales de RPCs que deben estar ausentes, en vez de enviar null o texto vacío. Revise los valores por defecto explícitamente; no se evalúan expresiones de plantillas. Actualice contrato y servidor juntos a una versión que incluya esta opción; la versión publicada 0.3.0 no la implementa.

## Metadatos para edición

Los anfitriones embebidos pueden proporcionar `queryCatalog` a
`createDashboardHandler` o `serve`. La ruta GET opcional `query-catalog` del
dashboard verifica el permiso de edición antes de solicitar conexiones y
operaciones activas y autorizadas. Solo devuelve IDs, etiquetas y nombres de
columnas opcionales; excluye esquemas de ejecución y credenciales y no se almacena
en caché. Sin proveedor devuelve 404. El anfitrión limita el trabajo de consulta y
respeta la cancelación; la ejecución vuelve a autorizar cada solicitud. Consulte
el README del paquete para los límites y tipos del proveedor.
