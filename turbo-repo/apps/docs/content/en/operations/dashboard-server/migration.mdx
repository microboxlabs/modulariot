# Migrating Planner Dashboards

Legacy dashboards load data with a request planner: each request calls a PostgREST path through a legacy data source. The dashboard server runs saved queries instead. Each saved query names a connection operation that an integrations admin creates. Widgets keep working because a saved query keeps the planner request's `variableName`.

## What you need

| Legacy | Dashboard server |
|---|---|
| Data source | One `POSTGREST` connection with its credential profile |
| PostgREST path, such as `rpc/fn_summary` | One read-only `HTTP_GET` operation on that connection |
| Planner request | One saved query in the dashboard |
| `{{filter.key}}` parameter value | Filter binding, omitted when the filter is empty |
| Other parameter value | Literal binding |
| Implicit date filter | Declared `date_range` filter with key `date_range` |

Operations are shared: one operation serves every dashboard that calls the same path on the same data source.

## Steps

1. **List the operations.** Pass the legacy configs to `plannerOperationContracts`. It returns one contract per data source and path, with every parameter any dashboard passes.

   ```ts
   import { plannerOperationContracts } from "@microboxlabs/miot-dashboard-server";

   const result = plannerOperationContracts(legacyConfigsBySlug, {
     pinnedParameters: ["p_client_id"],
   });
   ```

   A pinned parameter is fixed with `const`, so a dashboard cannot change it. It must have the same literal value in every request that uses the path. `result.problems` lists POST requests, unsupported paths and conflicting pinned values.

2. **Create the connections and operations.** For each data source, create a credential profile and a `POSTGREST` connection, and test it so it is `ACTIVE`. Then create each contract as an operation:

   ```bash
   miot connections operations create <connectionId> \
     --name fn_summary --method GET --path /rpc/fn_summary \
     --request-schema-json "$SCHEMA" --response-schema-json '{}' --output json
   ```

   Record each operation `id`.

3. **Convert the dashboards.** Give `migratePlannerQueries` one mapping per planner request. Leave out `parameters` to derive the bindings from the legacy values.

   ```ts
   const converted = migratePlannerQueries(
     legacyConfig,
     requests.map((r) => ({ plannerId: r.id, connectionId, operationId: ids[r.pgrestFunctionName] })),
     { dateFilterLabel: "Date" },
   );
   ```

   The result removes `requestPlanner` and keeps widgets, filters and other settings. When a binding reads `date_range_from` or `date_range_to`, a `date_range` filter is added.

4. **Save and compare.** Save each converted dashboard, then compare it with the legacy page using the same filters.

## Operation contracts

A generated request schema looks like this:

```json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "p_client_id": { "type": "string", "const": "client-1" },
    "p_from": { "type": "string", "maxLength": 2048 }
  },
  "required": ["p_client_id"],
  "x-dashboard": { "readOnly": true, "kind": "HTTP_GET", "credentialScoped": true }
}
```

| Requirement | Why the call fails otherwise |
|---|---|
| The connection credential sends `authorization`, `x-api-key` or `apikey` | Other header names are refused |
| The connection base URL uses `https` | HTTP_GET operations resolve only to `https` URLs |
| The base URL origin is in `MIOT_DASHBOARD_DATA_ORIGINS` | The dashboard server refuses other origins |
| Every result value is a scalar or an array of scalars | A row with a JSON object column fails the whole query |

When a function returns a JSON column that no widget uses, add a pinned `select` parameter with the scalar columns, for example `{ "type": "string", "const": "id,total,status" }`, and a literal `select` binding with the same value in the saved query. PostgREST then returns only those columns.

## Choosing operations while editing

The saved-query editor lists connections and operations from a query catalog. With the ModularIoT operations module, set `MIOT_DASHBOARD_CATALOG_URL` to the modulith's `/internal/dashboard-operations/catalog` endpoint. It uses the same service key as `MIOT_DASHBOARD_PLAN_URL`. Without it, the editor reports that the catalog is unavailable; saved queries still run.
